# Native iOS port: plan

Drafted 2026-10-31 from main at `b0861bb`. Planning only; nothing here is built
yet. Read [docs/autopilot.md](../autopilot.md) first: it is the one place the
prototype's intent is already written down.

## What we are protecting

The web prototype is done, and it is the reference. Two kinds of things are in
it:

- **Behavior** (hard requirement): what the player sees and what the app
  learns from them. Which moves count as prep, how a miss is judged, when a run
  ends, what a rating does after an answer, which position the next run starts
  at, what Growth offers, what Tidy suggests, every number and every word. The
  port must reproduce all of it.
- **Structure** (free to change): files, state management, React hooks, the
  persisted JSON shape, how engine searches are queued. The port should use a
  clean design built for what the prototype ended up being, not for how it got
  there.

The worry is that details settled over ~60 decision threads (September 13 to
October 31) get lost. So the plan's core is a **parity system**: a written
behavior spec, plus golden test cases generated by running the prototype's own
code, which the Swift app must pass before any feature counts as ported.

## What reading the prototype turned up

These shape the plan. Each one is a way details could get lost.

1. **The run logic lives inside React screens.** The Survival run, which is
   also every Autopilot round, is driven by `SurvivalScreen.tsx` (1,078 lines):
   the prep status latch (On prep, Prep complete, Off prep), when the book
   phase starts and ends, how a miss is tallied and rated, what pops over the
   board, when a run is logged as a clean finish or a stub, and what the end
   screen gets. That logic is spread across `useEffect`s, refs and timers. The
   same goes for `GrowthScreen.tsx` (980), `DrillSession.tsx` (722),
   `LineDrill.tsx` (451), `End.tsx` (484) and `OnboardingScreen.tsx` (658).
   **None of it has tests**: the 971 existing tests cover `src/model` and
   `src/store` only. This is the biggest risk, because a port agent reading the
   screen will see React plumbing and has to guess which parts are rules.
2. **The README is out of date.** Its Autopilot section still describes a
   ten-second clock, focuses and checkpoints; Repair is described as a mode.
   The decision notes in project memory are newer, but they are a history:
   later notes override earlier ones. Neither can be handed to a port agent as
   the spec as it stands.
3. **There is dead code.** `openingRun.ts` (1,398 lines) is mostly the old Run
   mode, with only some parts still used by Survival (`prepIndex`,
   `regionSource`, `BOOK_SHARE`, `judgeByEval`). The recommendation focuses,
   Repair's model, and Growth's past-the-book engine reply plumbing are partly
   or fully unreachable. Porting them would waste time and could bring back
   behavior that was deliberately removed.
4. **Behavior depends on things that aren't deterministic.** These are the
   engine's evaluations, `Math.random` (opponent replies, Any favorite, drill
   order), `Date.now` (cards, ratings by day, streaks) and the book data. A
   test can only compare the two apps once all four are fixed inputs.
5. **Two deliberate changes are coming.** Caissa replaces Stockfish, and
   level-matched books replace the 2200+ Lichess Elite book. Both change
   behavior on purpose. If they ship together with the port, a failing
   comparison can't tell a port bug from an intended change.

## The parity system

### 1. A behavior spec in the repo

`docs/spec/`, one file per area (list in the appendix). Each rule is short,
numbered and testable:

> **SURV-14** A move your prep doesn't have, at a position where it has one,
> is a miss. It is logged and rated against the position you were asked about,
> and the run goes on unless the engine calls it a blunder (80cp, see
> SURV-20). The prepared move flashes green for 2s.
> *Source: survival-mode-redesign (09-25), rating-per-opening (09-21).*
> *Cases: `survival/miss-*.json`.*

The rules:

- The **code is the source of truth for what happens**. The decision notes say
  why, and they flag where the code drifted from what was agreed. Each
  conflict goes into a list for the owner, not silently resolved.
- Every rule names its **source** (a decision note or a commit) and the
  **cases** that cover it. A rule with no case is a gap the coverage report
  shows.
- Every rule is marked **port**, **drop** (dead or superseded) or **change**
  (an intended difference, for example the book). Only the owner moves a rule to
  drop or change.
- **Constants** (thresholds, caps, timings) live in one generated file,
  `spec/constants.json`, extracted from the TypeScript. The Swift app has a
  test that its constants equal that file, so nothing like `COLD_EVERY = 3` or
  `MISS_MS = 2000` drifts quietly.
- **Copy** gets the same treatment: `spec/copy.json` lists every user-visible
  string with where it shows. The port reuses it rather than retyping it, which
  keeps the American spelling, the no-captions rule and wording such as
  "% of strong players' games" intact.

### 2. Golden cases both apps run

Language-neutral JSON in `spec/cases/`, generated by running the prototype's
real code (`npm run spec:cases`), never written by hand. Each case is
`{ input, expected }`. The Swift test target loads the same files. There are
two layers.

**Function cases** cover the pure model: the rating step, tiers, SRS review
and `runNeed`, `gradeForTime`, `chooseStart`, `prepIndex`, the prepared floor,
`isBookMove`, `lineKinds`, `growOfferAt`, `growthRows`, `nudgeArrows`,
`tidyFinds`, `glowFor`, `moveScore`, combo, moments, missions, milestones,
`familiesIn`, and so on. For each function: the cases from its existing unit
tests, plus edge values around every threshold (79/80/81cp, 4.9/5/5.1%,
2.9/3/8s), plus randomized inputs from a seeded generator. Today's 971 tests
already exercise most of this; the generator mostly reuses their inputs and
records outputs.

**Scenario cases** cover whole runs, driven through a mode's pure controller
(`survivalController` and the rest). A scenario is written in
`src/spec/scenarios/<area>.scenarios.ts` as a short script: your moves with
their times and the engine's verdicts, and the engine's replies where the
book has none. A driver resolves the script into the exact controller calls
the screen makes, in the screen's order, and the generated JSON in
`spec/cases/scenarios/<area>.json` keeps those calls, so the native tests
replay the calls with no driver of their own:

```json
{
  "name": "clean-prep-into-the-book",
  "setup": { "reps": [...], "start": { "steer": "lines", "node": "...", "color": "w", "seed": 3 },
             "picker": 5, "prefs": {...}, "autopilot": true, "kinds": {}, "losses": {} },
  "steps": [
    { "call": { "fn": "playPrepared", "san": "d4", "seconds": 1, "now": 1790845201000 },
      "effects": [{ "kind": "buzz", ... }, { "kind": "answered", ... }, { "kind": "pop", ... }, { "kind": "rate", ... }],
      "after": { "played": ["d4"], "prepStatus": "on", "bookTo": null, "extras": {...}, ... } },
    { "call": { "fn": "bookTurn" }, "effects": [], "after": { "played": ["d4", "d5"], ... } }
  ]
}
```

Each step's `effects` are what the screen carries out, in order (pops, notes,
ratings, card reviews, mistakes, the finish), and `after` is the session as
the run decides it. The opponent's book moves come from `mulberry32(picker)`,
and the engine's verdicts are data in the call, so no engine runs. What the
screen does with the effects (the end screen, the store) is covered by the
e2e traces and, later, by the store's own cases.

Scenarios to cover first, the Autopilot path:

- Position, inside and cold starts, including first run of an opening, the
  every-3rd-run cold backup, never two inside or cold starts running, and
  inside starts only at positions a run already asked.
- A clean prep, a miss (at your first prep move, mid-line, at a transposed
  position), a stub opening that asks nothing, and a saved mistake played as
  prep.
- The book phase: entering, a book move, a non-book move ending it, the book
  running out, the 5% line.
- Endings: blunder (threat arrow, Continue), mate, draw, End round from move
  one, X with no end screen.
- The end screen: Final position and End of prep tabs, ratings card, Grow this
  line for a stub, for a ready opening and at an unanswered reply, the
  embedded Growth batch and Next round.
- Any favorite and the selection rules: one favorite per round, side
  switching, played-longest-ago odds.
- Run-counted need: a card's need over runs, `testedRound`, `RUNS_PER_DAY`.

### 3. A determinism contract

Both apps take the four non-deterministic inputs through the same small
interfaces, so a scenario can fix them:

| Input | Contract |
| --- | --- |
| Random | One seeded generator, `mulberry32`, specified bit for bit. Each decision draws in a documented order. |
| Time | An injected clock. "Now", move timings and day keys come from it. |
| Engine | An `Engine` protocol. Scenarios use a scripted engine that replays recorded answers per position (score, best move, pv, multiPv lines), so verdicts don't depend on Stockfish or Caissa. |
| Book | Pinned to the prototype's `book.json` for every parity case. |

The scripted engine answers are recorded once from the prototype's real
Stockfish and stored with the case. Engine quality is checked separately (see
6).

### 4. Prototype work this needs

The prototype has to change a little so its behavior can be captured. None of
this changes what the player sees.

1. **Extract the run controllers.** Move the rules out of `SurvivalScreen`,
   `End`, `GrowthScreen` and the Drill screens into pure reducers
   (`state + event → state + effects`), with the screens rendering them. This
   is the step that makes scenario cases possible, and it's also the clean
   design the Swift app should copy. To make sure the extraction changes
   nothing, a small set of browser tests (Playwright, scripted engine) records
   the Autopilot flows **before** it starts and must still pass after.
2. **Inject the four inputs** (random, time, engine, book) where the model and
   controllers reach for them directly today.
3. **A dead code audit.** Run an unused-export tool and an end-to-end
   coverage pass, then list everything unreachable for the owner to confirm as
   drop.
4. **Generators**: `spec:constants`, `spec:copy`, `spec:cases`, and a coverage
   report of rules without cases.
5. **Freeze rule.** From here on, any prototype change also updates its spec
   rule and regenerates the cases, so the reference never drifts from the
   spec.

### 5. Real player data as a corpus

The Playbook tab's Export as JSON gives a real, messy state. Run the
prototype's derived views over it and store the results: Playbook family rows,
Tidy finds, Extensions kinds, Growth rows, rating tiers, Home's widgets,
milestones, and the next 50 Autopilot rounds under a fixed seed. Synthetic
fixtures miss things real data hits (the Tidy hint and the empty Queen's
Gambit bugs were both found only on real lines). The corpus also tests the
importer if the native app reads web saves.

### 6. Engine calibration, kept separate

Parity cases never touch a real engine. Caissa gets its own acceptance test
instead: a benchmark of positions with known answers (the 60-popular-book-move
false-blunder bench from the backup engine work, past false-blunder
reports such as 13.Ne4 in the QGD, real blunders such as 4.Nc3 in the
Chigorin) run through the judge's exact procedure (joint multiPv 2 search,
0.7s quick verdict, depth 16 within 4s on suspicion). Pass: no more false
blunders than Stockfish in the web app, and every known blunder caught. The
same bench checks moments (150cp gap) and the move score popups.

### 7. UI parity

- `spec/tokens.json`: colors (tiers, book `#4fb3ff`, extension `#8a8cff`, plan
  cyan `#22c3e6`, glow), spacing, radii, fonts, extracted from `styles.css`
  and `board.css`.
- A reference screenshot set from the web app (Playwright, fixed state, seed
  and scripted engine) for every screen and important state: run states, pops,
  the miss flash, the blunder threat, end screen tabs, rating card playback
  frames, the round intro plate. The Swift app renders the same states in
  snapshot tests, and each pair is reviewed side by side. Text won't match
  pixel for pixel, so this is a review, not a diff.
- The timing table from `spec/constants.json`: miss flash 2s, score pop 1.4s,
  note 1.6s, Undefended flash 1.3s, opponent beat 420ms, intro 2.5s, autoplay
  0.4s a move, verdict flash 2s.
- Board drawing rules from the decisions: arrowheads drawn after every shaft,
  pieces above arrows, dark arrow edges, a disc under an arrow's start piece,
  role arrow colors and pattern glow.

### 8. Done means

A feature counts as ported when:

1. every **port** rule in its spec area has at least one case,
2. all its function and scenario cases pass in Swift on CI (GitHub Actions
   macOS runner),
3. its screenshot pairs are reviewed, and
4. the owner has played it on TestFlight.

The coverage report is the progress bar for the port.

## Native shape (to refine)

A sketch, to be designed properly once the spec exists:

- One repo. The Swift app lives in `ios/` next to the prototype, so both read
  `spec/` directly and a prototype change that regenerates cases breaks the
  Swift build until it's ported.
- Swift packages: `ChessCore` (board, SAN, FEN, perft-checked), `Book`,
  `Model` (pure, one module per spec area), `Engine` (Caissa behind the
  protocol, an actor with a search queue), `Store` (persistence and sync),
  and the SwiftUI features.
- Each mode is a reducer plus effects, the same shape the prototype refactor
  produces, so a scenario case drives the Swift reducer exactly as it drives
  the TypeScript one.

## Phases

| Phase | What | Exit |
| --- | --- | --- |
| 0. Audit | Live code map, dead list, drift list (code vs decisions), owner confirms port/drop | Signed-off area list |
| 1. Spec and harness, whole app | Inject inputs, extract every mode's controllers, browser safety net, spec for every area, generators, cases | Cases pass on the prototype, coverage 100% for every **port** rule |
| 2. Native foundation | `ChessCore`, `Book`, core `Model` (tree, Playbook, SRS, ratings, selection) | Function cases pass in Swift |
| 3. Autopilot | Run controller, judge, end screen, Grow this line batch, Home, round intro | Scenario cases and screenshot review pass; TestFlight |
| 4. Rest of the free tier | Playbook tab, Tidy, Extensions, Onboarding, Stats, Milestones, Analysis, Play | Same, per area |
| 5. Paid modes | Survival setup and extras, Drill positions and lines, full Growth, import | Same |
| 6. Intended changes | Caissa (calibration bench), level-matched books, paywall | Each lands as a spec **change** with regenerated cases, one at a time |

Decided 2026-10-31: the whole app is specced and covered by cases
before any Swift, so the reference is complete up front. Phase 1 still starts
with Core and Autopilot, since everything else builds on them.

## Decisions

Settled 2026-10-31:

1. **Test work up front:** the whole app is specced and covered by cases
   before any Swift.
2. **Dead code:** everything unreachable from the app's entry point (about
   1,200 lines: the old Run model in `openingRun.ts`, the sample repertoires
   and their seeder, `gaps.ts`, Repair leftovers, the picker's sorts, unused
   helpers) is left out of the spec and the port, and deleted from the
   prototype in phase 1. Logic that is reachable but can't be turned on is
   raised one item at a time while the spec is written.
3. **Web saves:** the native app starts fresh. No import.
4. **Books:** port on today's 2200+ book. Level-matched books come after, as
   their own spec change, with the 5% book line and the 15% prepared floor
   re-tuned on the new data.
5. **Mode Testing:** not ported, and removed from the prototype in phase 1
   along with the dead code.

## Appendix: areas and the details to capture

A first inventory from the code and the decision notes. Each becomes a spec
file. Numbers are current values on main.

**Core**
- Chess rules, SAN/FEN, position keys that ignore move order (transpositions
  count everywhere).
- The book: 2200+ Lichess Elite, linked child positions, "% of strong players'
  games", book move = at least 5% and not an engine mistake.
- Opening tree and naming: deepest book name, family rows, `nameForBlack`
  ("1...e5"), regions (reached, on the way, outside), custom nodes for any
  legal line, "Slav › Modern Line › 3...Bf5" trails.
- Playbook: moves with source labels (ten kinds), `addedAt`, `keptAt`, cached
  engine loss, prune rules, events log (cap 1000), Undo.
- Selection: one node and side, Any opening, Any favorite (one favorite a
  round, played longest ago, each next rank half as likely, never the same
  twice), cards judged by their answer.

**Learning**
- SRS cards: steps 1 and 10 min, ease 2.5 (min 1.3), interval rules,
  `gradeForTime` under 3s easy, under 8s good, else hard. Line cards keyed by
  tip id.
- Need counted in runs: `testedRound`, learning gap 2 runs, review interval
  times 3 runs a day.
- Ratings: Elo-shaped, step 20, scale 450, floor 0. Only Survival and Autopilot
  rate, only prepared positions, credited to the position asked, for every
  opening the run's line reaches (answers before it got there are added when
  it arrives). Tiers Learning 100, Familiar 250, Solid 400, Strong 550, Fluent
  700, Mastered 850, New and Shaky below. Extensions sub-rating; saved
  mistakes never rated.
- Clean finishes (3 per leaf line), stubs (not logged as perfect), mistakes log
  (cap 200), a correct answer clears its mistake.

**Autopilot**
- Every round a Survival run. Starts: position (default), inside (most overdue
  in runs, weak fallback while prep accuracy slips), cold (way-in need over 6
  runs). Never two inside or cold starts running, cold at least every 3rd,
  first run of an opening always a position start. Starts saved across
  sessions (last 6).
- Opponent: book by share, only moves of at least 5% plus your prepared
  replies; every prepared reply lifted to at least 15%, lifted replies sharing
  at most half; steering by lean; then Play's Club level past the book.
- Feedback: "✓ 2.1s" in speed tone, "✓ Book", "✓ Ext", saved-mistake red
  cost, prep segments (prep, then book, outlined extension), "+N" rating chip,
  prep status label (On prep, In the book, Out of book, Off prep).
- Book phase after a clean prep; book moves count for points and combo,
  never for ratings or cards.
- Ending: blunder 80cp by one joint search, threat arrow, Continue; End round
  from move one; mate and draw.
- End screen: Final position and End of prep tabs, rating card playback
  (level up and down animations), prep summary, one Grow this line, Analyze
  over the mode with Back.
- Own settings only (move scores, glow, Mode Testing). No mode's setup ever
  reaches Autopilot.

**Survival extras** (paid, but Autopilot runs them)
- Move scores as swings since your last scored move, never 0, yellow to −40.
- Glow: nothing within ±100cp, green full at +500, yellow at −100, red from
  −300, full at −700.
- Combo ×1 to ×4 at 0-2, 3-5, 6-9, 10+, within 20cp extends, 40cp holds.
- Moments: top-two gap of 150cp and best at +1 or better; a miss judged
  against the second best; +10 then +5 a streak.
- Missions: edge, lead, dig, plan, convert, windows and bonuses (+15), a
  3-move break between them.
- Lenses, plan cards with text only, Cash out at +200.
- Records: best moves survived, points, recent form (median of 5), history of
  16, ended runs counted apart.

**Growth**
- Batch size from plies left to the horizon, halved, capped at 8. Starts at
  the first answerable hole (reach × share). Stops at the book's edge. List
  ordered by strong-player share, then eval change. Role arrows (blue strong,
  purple engine) with nudge glow and pills. Undo, Undo all, Done. The back
  card and practice cap by line count (3, 2, 1).

**Playbook tab, Tidy, Extensions**
- Family rows, line rows, delete with confirm and Undo.
- Tidy: habits within ±4 plies in the opening and its kin sets, named setups,
  transpositions and "heads toward", switches reset the position's card and
  mistakes but keep the rating loss.
- Extensions: kinds (rare, mistake, past the book), review graph layout rules,
  only your own moves start one.

**Onboarding, Home, Stats, Milestones**
- Starter sets, Pick openings, play on the board, only the openings' own
  moves, nothing saved until Ready.
- Home: Autopilot plate (board behind the name, segments), tiles, Survival
  runs chart, Favorites ladder, Milestones (18).
- Stats: Favorites, Rated, per-opening pages.

**Play, Analysis, Drill, import**
- Play levels, the opening's move order, games kept (cap 200, 40 plies).
- Analysis: absolute scores in White's frame, Back to the end screen.
- Drill positions and lines (budget 15 of your moves, up to 3 lines, batch
  similar), Draw from.
- Import and the evidence feed into steering.
